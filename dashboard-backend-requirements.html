2 Decision: who computes the aggregations?

Option A — frontend computes

Backend only adds one activity endpoint. Frontend keeps its computed() math.

Option B — backend computes ✅ recommended

Dedicated dashboard endpoints return the numbers. Less data over the wire, real persistence for activity.

3 Endpoint 1 — Dashboard summary

GET /api/dashboard/summary?days=7

No request body. Query param days optional, default 7.

FieldTypeMeaning
totalBooksnumberCount of Book titles
availableCopiesnumberSum of availableCopies across all books
activeBorrowingsnumberBorrowRecords with returnDate = null
overdueBorrowingsnumberreturnDate = null AND dueDate < today
availabilityRatenumber0–100, rounded (see warning below)
totalAuthorsnumberCount of Authors
weeklyActivity[]array{ date, label?, borrowedCount } — exactly days entries, zero-filled, oldest first
categoryBreakdown[]arrayMax 6, sorted desc: { name, count, percentage } — percentage of totalBooks

4 Endpoint 2 — Recent activity feed

GET /api/dashboard/activity?limit=6

No request body. Sorted by occurredAt descending, limit applied after sorting.

FieldTypeMeaning
idnumberUnique activity id
kindenumBORROWED, RETURNED, BOOK_ADDED, BOOK_DELETED
bookTitlestringAffected book's title
subtitlestringBorrower name (loan events) or Category name (catalog events)
actorNamestring?User who did it, nullable
actorRolestring?e.g. ADMIN / USER
occurredAtdatetimeReal persisted event time
⚠️ BOOK_DELETED problem: a hard delete leaves no record. Either soft-delete books, or drop BOOK_DELETED from the enum (frontend then shows 3 kinds). Decide deliberately.

7 ⚠️ The availabilityRate formula is broken

Current frontend math: availableCopies / (availableCopies + activeBorrowings) — wrong, because activeBorrowings counts records, not copies. Pick one:

OptionMeaningCost
Drop the rateShow plain "Available copies" cardFree
Add Book.totalCopiesrate = available / totalSchema change + migration
Count copies on loanSum of open BorrowRecordsHides a modelling assumption — don't do silently

8 Review checklist (how your code will be judged)

  1. summary endpoint exists, all fields, wrapped in ApiResponse
  2. weeklyActivity has exactly days zero-filled entries
  3. categoryBreakdown: denominator is totalBooks, max 6, sorted desc
  4. overdue = returnDate == null AND dueDate < today
  5. activity feed: no hardcoded rows, no invented titles
  6. occurredAt is a persisted timestamp, not "now" at read time
  7. BOOK_DELETED resolved deliberately (soft delete or enum reduced)
  8. availabilityRate follows your decision, not the broken formula
  9. greeting/actor names come from the authenticated user
  10. all endpoints JWT-protected, errors via GlobalExceptionHandler
